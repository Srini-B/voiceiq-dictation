# Agent rules

- Whenever the macOS application needs to be tested, test a signed and notarized build: produce it with the release flow (`scripts/release.sh`), install it, and test the installed app. Never test on a Debug build.
- Before installing a build to test on a shared test Mac, turn off Sparkle's automatic updates so the app under test is not replaced mid-run: `defaults write io.blue.voiceiq SUEnableAutomaticChecks -bool false; defaults write io.blue.voiceiq SUAutomaticallyUpdate -bool false`. On 2026-11-28 Sparkle replaced a probe's 0.7.17 build with 0.7.18 during the run.
- Never turn off Wi-Fi or any other network interface on a test machine (the Mac mini runner, the MacBook, or any remote Mac), not even briefly to test offline behaviour. These machines are remote; one lost its only network link for hours until someone rebooted it by hand. Test offline paths by blocking only the app's requests, or skip the test and say so.
- On a shared test Mac, take the app lock before quitting, installing or replacing `/Applications/VoiceiQ.app`: `scripts/app-lock.sh acquire <thread ID>`, then `scripts/app-lock.sh release <thread ID>` when done. A lock under 30 minutes old means wait; an older one is stale and can be taken. Tests that don't need the real install use their own copy, such as `~/Applications/VoiceiQ-<thread>.app`.
- Heavy jobs on the shared Mac mini (xcodebuild, swift test, simulator runs, release builds, signed installs, eval runs) take a turn in its queue: `scripts/mac-queue.sh wait <thread ID> release|merge|other "<what>"` before, `scripts/mac-queue.sh done <thread ID>` after. At most two run at once; release-gating jobs go first, then merge gates, then the rest. Shut down your simulators before `done`.
- Before launching or installing `/Applications/VoiceiQ.app` on a shared test Mac, take the app lock, check which build is installed (`defaults read /Applications/VoiceiQ.app/Contents/Info CFBundleVersion`), and check that the data folder holds no seed or test data. That app syncs to the owner's real iCloud.
- A test that creates dictations, meetings or Dictionary terms must not sync to iCloud. Neither a different bundle ID nor re-signing without the iCloud entitlement is enough. Every build writes to the same `~/Library/Application Support/VoiceiQ` (FileLayout), and the real app later uploads any finished meeting it finds there. Re-signed copies don't work either: granting them Accessibility and Screen Recording needs the admin password. Run such tests on the installed signed app in test mode (docs/DEBUG_LOG.md, Test mode), holding the app lock for the whole run. Quit the app and save its settings first: `defaults export io.blue.voiceiq <file>`. The Dictionary (auto-learned terms too) and other settings live there, not in the data folder, and would sync once sync is back on. Turn off Markdown export, which test mode doesn't stop and which may write into iCloud Drive: `defaults delete io.blue.voiceiq meetingMarkdownFolder` (the restore below brings it back). Then `defaults write io.blue.voiceiq DebugDisableCloudSync -bool true` and `defaults write io.blue.voiceiq DebugDataFolder /absolute/path`, launch it, and check that its menu shows "Sync off (test)" and "Data in <path> (test)" before creating anything. Test mode has its own Keychain keys (none in a new folder), so enter the AssemblyAI key in the test app's Settings, or put it in ~/.config/voiceiq/apikey.dev before launch. When done, quit the app, check the saved file is there, then restore the settings exactly: `defaults delete io.blue.voiceiq` followed by `defaults import io.blue.voiceiq <file>` (import alone merges, which would keep test terms and both test keys). Relaunch it, and check that neither "(test)" line is left in the menu before releasing the lock.
- Choose each release's version by semantic versioning (cyron's rule, 2026-11-28). Patch (0.7.x) is for fixes only. Minor (0.x.0) is for new features or notable changes, such as a new provider, a new key users must enter, or a new way dictation or meetings work. Major: 1.0.0 ships only when every scorecard item (activities/2026-11-26-quality-scorecard.md), meetings included, is at 90 or above and the release build has been checked on a real iPhone, not only the Simulator; after that, a release that breaks compatibility raises the major version. `CURRENT_PROJECT_VERSION` (the build number) still goes up by one with every release, whatever the version.
